# Production gap register

**Rule (`AGENT.md` section 3): every POC simplification must be registered here, not
silently ignored.** A change that deepens a shortcut without updating this register is an
incomplete change.

POC behaviour | production requirement | why it differs.

## Baseline (from `AGENT.md` section 3, registered in M0)

| Area | POC behaviour | Production requirement |
| --- | --- | --- |
| Transport | UDP only | UDP + TCP + TLS; TLS mandatory on public-internet trunks |
| Peer authentication | Source IP allowlist at most | IP allowlist + SIP Digest + TLS certificate (triple check) |
| Topology | Single peer, single trunk | Multiple S-SBC peers, failover routing |
| Core network | Mocked UAC/UAS in one process | Real S-CSCF, iFC triggering, subscription data |
| Header handling | Verbatim pass-through | Header normalisation, private extension stripping |
| Transactions | Happy path + a few error branches | Full RFC 3261 retransmission, timer and timeout handling |
| Reliability | Single process, no persistence | Restart safety, session recovery, watchdog |
| Media | None | SDP negotiation validation, optional media anchoring |
| Charging | None | CDR generation per call leg |
| Security | Local mock, dev-only | DoS protection, rate limiting, CAC, black/white lists |
| Observability | Console + log trace | Centralised collection, retention, alerting |
| Configuration | Local YAML + `.env.example` | Managed configuration service, secret manager |
| Capacity | Not measured | SLA-backed throughput and call setup latency |

## Additional gaps registered while building M4

| Area | POC behaviour | Production requirement |
| --- | --- | --- |
| Version discovery | **Resolved by P5.** The AS runtime version (`as_app.__version__`) is resolved by a three-step chain: `importlib.metadata.version("third-party-as-poc")` first, then the repository `VERSION` file (relative to `src/as_app/__init__.py`, the M4 fix), then `0.0.0+unknown`. An installed wheel no longer reports `0.0.0+unknown` because it carries distribution metadata even though it ships no `VERSION` file. **Remaining caveat:** the chain still needs the distribution metadata to be present and readable — a wheel installed without its metadata (or a vendored/`zipapp` copy of `src/as_app` with neither metadata nor `VERSION`) still falls through to `0.0.0+unknown`. Shipping `VERSION` as package data would close that last case; it is not needed for any supported install path. | Version reporting should not depend on where the code is installed from: derive it from the installed distribution metadata, and keep the `VERSION` file (or package data) only as the source-checkout fallback. |
| Closing a transaction manager mid-retransmission | **Resolved by P8a (2026-09-18).** sippy's `SipTransactionManager.shutdown()` still cancels only its own `cp_timer`; the repository now cancels what it armed first, in `as_app.sip_adapter.cancel_transaction_timers`, before handing the manager to sippy. Historical defect, kept for the record: a pending `timerA` used to fire after shutdown and dereference the then-`None` `global_config`, raising `TypeError: 'NoneType' object is not subscriptable` in `transmitData`. It hit the AS graceful-shutdown path (a transaction still retransmitting when the process exits) and it was the root cause of the rare (~1 in 6 full-suite runs) non-deterministic failure of `test_next_hop_failover_uses_the_second_hop`, where the in-process tests share one process-wide `ED2` loop. | Cancel every outstanding transaction timer on shutdown and drain in-flight transactions before exit. **Remaining caveat:** sippy itself is untouched — a third-party `SipTransactionManager` is still shutdown-dependent, and anything this repository arms outside `AsStack.stop()` has to be cancelled by whoever owns it. In-flight transactions are cancelled, not **drained**: no final response is sent to a peer for a transaction that was still retransmitting, so a far end that was mid-call sees silence rather than an error, which a production node would answer with a `503` / retry-after policy. |

## Additional gaps registered while building P1 (compose demo)

| Area | POC behaviour | Production requirement |
| --- | --- | --- |
| Rule set per environment | The trunk address lives in the rule set, because the AS originates the second leg to the hop `action.next_hops` selects and the routing engine resolves that name against the file's own `next_hops` catalogue. `SBC_PEER_ADDRESS` does not rewrite it. The POC therefore ships **two** rule files that differ only in the catalogue addresses: `config/routing_rules.yaml` (`127.0.0.1`, local runs) and `config/routing_rules.compose.yaml` (`172.28.0.3`, the compose network). The rule bodies are duplicated by hand and can drift. | One rule set per deployment with the peer addresses supplied by the environment — e.g. let a catalogue `address` be written as `${SBC_PEER_ADDRESS}` and expand it at load time (the SRS already makes all configuration environment-based, `AGENT.md` section 8). A managed configuration service would separate the dial plan (rules) from the peer inventory (addresses) entirely. |
| Rule set drift between environments | Nothing detects that the two POC rule files have diverged; only review catches it. | Validate every environment's rule set against one canonical source (generate, or schema-check that they differ only in the address fields). |
| Build-time package index | The Dockerfiles accept an optional package-index build argument (`PIP_INDEX_URL` / `UV_DEFAULT_INDEX`, so a build behind a slow or filtered network works). A non-default index makes uv re-resolve inside the image — a build-time, image-local `uv.lock` rewrite that keeps the pinned versions but re-resolves them from that index. The committed `uv.lock` always stays on public PyPI. | Build in an environment with the canonical index (or a mirror that is guaranteed identical), and verify the image with a reproducible provenance/SBOM step rather than trusting a build-time re-resolution. |

## Additional gaps registered while building P8a (2026-09-18)

| Area | POC behaviour | Production requirement |
| --- | --- | --- |
| Test port allocation | The integration tests allocate **every** port with `_free_udp_port()` in `tests/integration/test_signalling_path.py`, which binds and releases a **UDP** socket on loopback and returns that port number. UDP and TCP port spaces are independent, so the number proves nothing about TCP — including the internal API's HTTP port, which `test_counters_health_endpoint_and_graceful_shutdown` then polls. Observed once in 42 integration runs: `http.client.BadStatusLine: GET /healthz HTTP/1.1` — the connection was accepted by something that is not an HTTP server, so the health poll failed rather than waited. The same test passed 20/20 in isolation, and all 42 runs carried 0 `TypeError` tracebacks, so it is not a symptom of the P8a timer defect it was found beside. **Registered, not fixed** (`AGENT.md` §14 rule 4): the repair belongs to the test harness, not to P8a. | Allocate a port by probing the transport it will be used on — bind a `SOCK_STREAM` socket for a TCP port — and have the server bind port `0` and report the port it actually received instead of the caller guessing one. A health check must also tell "not up yet" from "something else is listening" (compare the response, not just the connection). |

## Additional gaps registered while building P8 (anti-fraud AS, 2026-09-19)

| Area | POC behaviour | Production requirement |
| --- | --- | --- |
| Cross-call anti-fraud state | The per-caller call-rate window and the reputation ledger live in one **process-level, in-memory** object (`src/anti_fraud_as/caller_state.py`). A restart loses them, and several AS instances cannot share them. The memory is bounded by `reputation.max_tracked_callers`, evicting the oldest caller first; there is no TTL and no eviction policy beyond that. | A shared, durable state store (Redis or equivalent) so state survives a restart and is shared by several AS instances, with a per-caller TTL and an eviction strategy. **This gap is deliberately left open**: it is one of the reasons P11's pluggable state store exists (`docs/phase2-plan.md` D9), and closing it here would remove that driver. |
| RFC 8688 section 3.4 announcement | The AS answers `608` **unconditionally**, whether or not the INVITE declared `sip.608` (section 3.4 requires the 608 to be forwarded as the final response either way). For a UAC that does **not** declare `sip.608`, the announcement obligation is therefore **unmet** — this signalling-only AS cannot play one (ADR-0006). The declaration state is recorded as `sip_608_declared` on every screened INVITE and a rejected call whose INVITE did not declare it increments `reject.sip_608_undeclared`, so the gap is observable rather than silent. | Play the announcement for a UAC that does not declare `sip.608`, or accept traffic only from UACs that declare it. Either way the request needs a media plane, which this POC deliberately does not have. |
| `Feature-Caps` reachability (interoperability) | The `sip.608` declaration is assumed to reach the AS. In a real IMS it originates at the **UAC** and must be forwarded by the S-SBC (RFC 3261 section 16.6). The POC cannot demonstrate that hop: the mock UAC, the mock S-SBC and the AS all run the same sippy stack on loopback, so the declaration arrives end to end by construction and the pass-through is untested. | Verify against a real S-SBC that `Feature-Caps` is forwarded unchanged before relying on the declaration. |
| Missing calling identity | An INVITE with no `P-Asserted-Identity` cannot be screened. The AS **fails open**: it records `verdict=allow`, `screen_source=none`, `identity_present=false` and relays the call, because no attestation mechanism is in scope (STIR is out of scope) and rejecting on a missing optional header would break legitimate traffic. **Security-relevant**: the failure mode is deliberate and visible, not silent. | Screen on a network-provided identity or on STIR attestation, or fail closed. |
| Caller redress (`Call-Info` / `jCard` / `JWS`) | No `Call-Info` header is sent with the `608`, so a rejected caller has no machine-readable redress address. Lawful under RFC 8688 section 6 — handing a suspected-abusive caller a contact address creates an attack vector — and the `jCard`/`JWS` mechanism is not implemented. | Implement the RFC 8688 section 3.1 redress mechanism for the jurisdictions that mandate it, together with the abuse handling behind the published contact. |
| Reputation and block/allow source | Reputation is **seeded** from the declarative data file and decayed locally; the lists are local data too. The data file is operator-supplied and separate from the AS's own logic (a local file in the POC, a service in production), so D4's "external source" holds — but **no live external reputation or portability service is queried**. A live lookup on the call path would need the same loop-owned, non-blocking treatment as the data-file reload. | Query an external reputation/NPDB source with a bounded, non-blocking lookup (cache plus loop-owned refresh), and treat its availability as a call-path dependency to be designed for. |
| Internal API duplication (P10 friction) | `src/anti_fraud_as/internal_api.py` duplicates the app factory and the uvicorn-on-a-daemon-thread server of `src/as_app/internal_api.py`, and `call_controller.py` mirrors that module's relay shell. The `as_app` versions are bound to a `RuleSetStore` and `/api/v1/rules`; parameterising them for a second use case now would be the framework P8 must not build (`AGENT.md` section 12). | Extract the shared internal-API surface and the B2BUA relay shell into the platform library, with the payload providers injected, so a third AS does not copy them a third time. Recorded as friction the P10 extraction inherits. |
| Retained call controllers (unbounded; inherited from Phase 1) | `FraudCallMap.controllers` keeps **one controller per call for the life of the process** and is never pruned. It exists so `dispose()` can cancel the timer of a call still in flight at shutdown. The structure is **inherited from Phase 1's `TrunkCallMap`**, which has the same shape, and P8 duplicates it in the second AS. Pruning was deliberately **not** added here: the map has no call-lifecycle signal, so the only safe-looking approximation (drop the oldest controller that has no armed timer) would be a *new, undesigned* behaviour that stage 4 has no test for. The honest fix is to register it, not to improvise it. | Bound the retained set and prune on call teardown, driven by an explicit end-of-call signal rather than a guess. Fix it **once**, in the platform library, for both AS instances (P10). |
| Header-name casing (`Feature-Caps`) | `Feature-Caps` is not a header sippy has a dedicated class for, so it is rendered by the generic header class and the mock's UAC emits `Feature-caps: *;+sip.608` — only the first letter is capitalised. RFC 3261 section 7.3.1 makes header field names case-insensitive, so the field and its value are correct; `P-Charging-Vector` → `P-charging-vector` already behaved the same way. | Normalise header names on the wire (or accept the caveat): a byte-for-byte conformance test against a real S-SBC still sees the difference. |
| `Feature-Caps` not forwarded on the allow path | The pass-through header set (`PASSTHROUGH_HEADERS`) does not contain `Feature-Caps`, so when the anti-fraud AS relays an **allowed** INVITE the UAC's `sip.608` declaration does not reach the next hop. "Relayed" therefore means the Request-URI, the SDP body and that header set — not the message in general (ADR-0007 decision 6, LLD section 9.6). | Decide per deployment whether `Feature-Caps` is a pass-through header — it is a capability negotiation between the endpoints, and this AS terminates the INVITE rather than proxying it — and widen the shared set deliberately if it is. |

## Additional gaps registered while building P9 (chained AS topology, 2026-09-19)

| Area | POC behaviour | Production requirement |
| --- | --- | --- |
| iFC / ISC emulation | The mock drives the chain as a **direct trunk call**: it sends one INVITE to AS-1 and AS-1 relays the allowed one to AS-2 by configuration, so no S-CSCF and no iFC are involved in placing the second AS in the chain (`tools/demo_chained_call.py`, `tools/chained_as_probe.py`). The two hops are wired by `FRAUD_SBC_PEER_*` on one side and a catalogue entry on the other (ADR-0008 decision 1), not by Initial Filter Criteria. | Model the S-CSCF trigger and the iFC/ISC that insert a second AS in the chain, so the AS order and the per-AS trigger conditions are decided by subscription data rather than by pointing one instance's next hop at the other. |
| Cross-AS trace correlation | **No surface can correlate the two instances' traces.** Every leg derives its own dialog `Call-ID` (`outbound_call_id()`), so a chained call carries **three** distinct values and the `Call-ID` the S-CSCF used cannot be joined to the one AS-2 or the core saw. The standard end-to-end key — the `P-Charging-Vector`'s **ICID** — **is** passed through the whole chain (measured: `ICID preserved: True`), but it is a **per-scenario literal** (`poc-{scenario.name}`, `MockUac._isc_headers`), not a per-call identity, and **no observability surface is keyed on it**: both instances key their trace, log, metrics and console feed on the `Call-ID` of their own trunk leg (LLD section 10.2, ADR-0008 decision 4). | Key the trace and console on the ICID, with a per-call ICID generated by the S-SBC, so one call is followable across both instances; or emit an explicit cross-instance correlation record. This is the observability contract of both AS instances and is P10's material. |
| Shared state between the two instances | AS-1's screening state (`caller_state`, screening data) and AS-2's rule set are independent processes and neither sees the other's decision; the chain carries no shared call context beyond what is on the wire in the pass-through headers. | A shared session/charging context if the chain ever has to make a joint decision, with the state store of D9 (the same driver that already makes the anti-fraud cross-call state a registered gap). |
| Routing catalogue coupling | AS-2's next hop is a property of the **matched rule** (a catalogue entry), not a peer setting, so the chain's tail cannot be changed without editing the rule file; the demo must rewrite the catalogue's next-hop ports to run on dynamic ports (`capture_call.rewrite_next_hop_ports`), which an environment-only wiring could not do (ADR-0008 decision 1, LLD section 10.1). | Separate the dial plan (rules) from the peer inventory (addresses) so a peer move is configuration, not a rule-file edit — the same rule-file-drift trap already registered for the compose environment, seen from the chained angle. |
| Chain failure, ordering and capacity semantics | P9 demonstrates the topology only: it shows an allowed call completing and a reject short-circuiting, but says nothing about what happens when **AS-2 is down**, how a failure at AS-2 propagates back through AS-1, whether the two instances' capacities compose, or what the ordering guarantees between them are. The probe's no-answer timer (3 s, `_DEFAULT_NEXT_HOP_EXPIRE`) is the only failure behaviour exercised, and only for one hop. | Define per-hop failure and timeout semantics (what AS-1 answers when AS-2 is unreachable), an end-to-end call-admission policy across the chain, and how capacities compose. Registered as P9.5's discovery input (`docs/phase2-plan.md`); not answered here. |

## Additional gaps registered by the P9.5 read-only capacity probe (2026-09-19)

`tools/capacity_probe.py` places concurrent calls at an escalating offered load against the
real chained topology and observes what degrades first. It publishes **no** calls-per-second
and no latency figure (`docs/phase2-plan.md` §8 item 1, D10); the rows below are the
constraints it found, each a boundary rather than a benchmark. No file under `src/` was
changed.

| Area | POC behaviour | Production requirement |
| --- | --- | --- |
| No-answer give-up does not fire on the failover hop | Towards an unreachable hop the controller logs `next hop did not answer in time` **once per call** and `trying failover hop` once, and then nothing: the failover hop's own 3-second no-answer timer (`_DEFAULT_NEXT_HOP_EXPIRE`, `src/as_app/call_controller.py`) never fires, so the application never gives up and the trunk is **not** released inside a window several times the nominal timeout (measured `0 of 4` after 9s and `0 of 4` after 25s). | A no-answer timeout must be armed on **every** hop the failover path tries, and the give-up must be bounded by the configured timeout regardless of how many hops the rule set lists — otherwise a peer that is silently down holds the call until sippy's transaction timers reap it. |
| `timerB` is the effective give-up | The call is ended not by the application but by sippy's client transaction timer: `timerB` = 32s reaps the transaction towards the silent hop, and only then is the failure relayed and the trunk released. The application's own 3-second decision is inert on the second hop, so the caller waits ~32s for a failure the AS decided on in 3s. | The application's decision must be the thing that ends the call: the give-up it decides on must be emitted as a response, not left to the transport stack's transaction timeout. |
| Armed transaction population and a table that is not reaped | Each call leaves one armed client transaction **per hop tried** (the shipped mobile rule lists a primary and a failover hop), each armed for `timerB` = 32.0s: a 4-call burst measured `8 of 8` armed, with `36` INVITE transmissions (`timerA` doubles its interval and only `timerB` stops it). Once `timerB` has fired, the transactions are still present in `SipTransactionManager.tclient` (measured `8` entries, `0` with `timerB` armed), so the reap does not clean the table. | Bound the in-flight transaction population under a burst and guarantee the transaction table is reaped when a transaction ends, or the timer heap and the table grow with burst × hops and never shrink. |
| Event loop as the serialisation point | One blocking, single-threaded `ED2` dispatcher serves both AS instances and the mock in this harness. Every call still completed at every offered level up to **64** concurrent calls, so no completion ceiling was found in the configured range; the observable constraint is the loop gap, which grew from `0.03s` at offered level 1 to `0.12s` at 64. In production each instance owns its own process and its own loop, so the number of instances is not what this measures. | Keep per-instance work off the shared dispatcher, or accept that a busy loop delays every call's timers and responses alike; capacity must be stated per instance and per process, not for the chain as a whole. |
| No admission control or back-pressure | Inside the configured range the chain has **no completion ceiling and no refusal**: all 64 concurrent calls completed and no `503` was ever observed, so nothing actually degraded — but there is no admission control or back-pressure to refuse or shed a burst, and the only limit that converts a slow call into a failed one is the fixed 3-second wall-clock no-answer timeout. | An end-to-end call-admission policy across the chain (per-peer and per-instance limits, overload signalling) so a burst is refused or shed predictably instead of being absorbed until wall-clock timers start failing calls. |

## Additional gaps registered while building P10 (platform extraction, 2026-09-19)

The extraction moved the skeleton shared by the two AS instances into the `as_platform`
library in a separate repository (ADR-0009). The rows below are the gaps the split accepts;
this documentation commit changes no file under `src/`.

| Area | POC behaviour | Production requirement |
| --- | --- | --- |
| Versioned consumption | The library is consumed from a filesystem path (`../as_platform`, `editable = true`), not a registry, so there is no version resolution and no pin enforcement — a version constraint in `dependencies` is silently ignored for a `path` source — and **no lockfile constraint either**: `uv sync --frozen` accepts a version skew and leaves the lock stale, while `--locked` refuses it. Neither the pin nor the lock guards the library; what catches a skew is a **gate**, not a lock (ADR-0009 decision 6, *Verified facts* (c)/(d)). | Publish the library and consume it by version (a wheel or a pinned VCS source), keeping the compatibility matrix as the contract. |
| Library interface induced from two instances | Exactly two samples shape `PolicyDecision`, `Transport` and `StateStore` (D2, ADR-0007 decision 9), so a third use case may show a dimension neither has. The seams are the mitigation, not a proof. | Validate the seams against a third use case before freezing the interface; record the dimensions the two samples establish in the compatibility matrix. |
| No second transport, no external state store, no capacity harness | The library defines `Transport` / `StateStore` and ships **one** implementation of each — `UdpTransport` and `InMemoryStateStore` — so the in-memory store remains the only store and no load/capacity harness is built (decision 5, REQ-NF-020). | Add TLS and Redis behind the existing seams and a capacity harness — all of which are P11's (D9, D10); building them now would remove a reason P11 exists. |
| Library scope: no mock, no console | The library carries **no mock S-SBC and no console**; a library-only consumer brings its own trunk peer and its own UI. | Ship a reference trunk peer and console (or a documented integration kit) so a third-party consumer can stand the library up without this repository's mock and console. |
| `extract_called_number` naming debt | `extract_called_number` keeps a name that is wrong for the anti-fraud caller (it parses a URI user part); the naming debt is recorded, not fixed. The unused `TrunkMessage` was **deleted with the move**, not carried (decision 2). | Rename it to a name neutral to both callers as a separate, approved change touching both applications. |
| Library gate not in this repository's CI | The library carries its own `ruff` / `mypy` / `pytest` gate (REQ-NF-021), but that gate does **not** run in this repository's CI, so a library change can pass here while failing the library's own gate (decision 8). | Wire the library's gate into this repository's CI (or a shared pipeline) so a library change is verified where it is consumed as well as where it lives. |
| `REQ-F-023` text names a moved location | `REQ-F-023`'s text says the `AS-FRAUD-*` codes are added to the authoritative model in `src/as_app/errors.py`; after the split the **mechanism** is the library's and the family lives in `src/anti_fraud_as/errors.py`. The requirement is **not reworded**; the delta is recorded in the SRS traceability note and `AGENT.md` section 4.3 (decision 3). | Keep the requirement text frozen per the stage rules and carry the location delta in the traceability note (as `REQ-F-011` does); a later SRS revision restates the location. |
| Consumption probe's stand-in scope | `tools/path_dependency_probe.py` measures `uv`'s resolution and install behaviour against a **two-module stand-in** library, not the real skeleton, so it says nothing about the extraction itself or the runtime of the extracted code. | Re-measure against a real published artefact; the extraction itself is covered by this repository's three layers and the committed probes. |
| CI second checkout (new dependency) | Every CI job clones the library repository into `../as_platform` before `uv sync --frozen`, because the `path` dependency cannot resolve without a sibling checkout (ADR-0009 decision 6). The clone needs the library **published at a real remote** (`<owner>/as_platform`); the library has **no remote configured yet and has never been pushed**, so CI is not green until it is. The existing lock comment ("`uv sync --frozen` … fails when …") is true for **registry** dependencies and **not** for this path dependency. | Publish the library repository at a real remote (and, later, consume a versioned artefact) so a fresh clone of this repository resolves its dependency in CI; treat the lock as a guard for registry dependencies only. |

## Notes

- Gaps are never "forgotten features": each one is a decision with an ADR or a row in this
  table. `ADR-0003` (UDP only), `ADR-0006` (signalling only) and the M3 console gaps
  (poll-based event feed, no browser verification) are the largest.
- When a milestone closes a gap, move the row out of this table into `CHANGELOG.md` and
  record which acceptance item covers the new behaviour.
